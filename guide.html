How to build a faceless YouTube Shorts pipeline on Windows

The exact free stack — Python + ffmpeg, free text-to-speech, free stock b-roll APIs — plus the part nobody publishes: what the view counts actually did afterwards. Every command below is from a pipeline that is running in production, and every number is measured, not estimated.

Updated 2026-08-20 · ~9 min read · Written with AI assistance and human-reviewed. See the disclosure.

What you are building

One long 16:9 video goes in. Vertical 1080×1920 clips come out — each one a distinct moment with a clean blurred background, ready to post as a YouTube Short, a Reel or a TikTok. It runs from one command on Windows, on a laptop, with no GPU.

Four free components do all of the work:

  • Python + ffmpeg — the actual video math (the only hard requirement).
  • A free TTS voice — for narration when you are generating original video rather than clipping an existing one. Fish Audio has a free tier that sounds human.
  • Pexels and Pixabay APIs — free stock b-roll, pulled programmatically so nothing is downloaded by hand. Both issue API keys at no cost.
  • Remotion (optional) — React-based renderer, if you want animated lower-thirds and on-screen charts instead of plain cuts.

Step 0 — Windows prerequisites

Install Python 3.10+ and ffmpeg, then confirm ffmpeg is on PATH:

winget install --id Gyan.FFmpeg -e
winget install --id Python.Python.3.11 -e
ffmpeg -version
Windows-specific gotcha that costs people an evening. If you run this from git-bash / MSYS, path arguments are not translated for native programs. ffmpeg /c/Users/you/clip.mp4 fails while cd /c/Users/you works. Pass native forward-slash paths (C:/Users/you/clip.mp4) to ffmpeg, node and python.

Step 1 — the core 16:9 → 9:16 converter

This is the whole trick, and it is one ffmpeg filter chain. Scale a copy of the frame up to fill the vertical canvas, blur and darken it as the background, then overlay the original at full width, centred. No black bars, and captions burned into the source stay readable because the foreground keeps its full width.

The filter chain used in production:

[0:v]scale=1080:1920:force_original_aspect_ratio=increase,crop=1080:1920,boxblur=20:2,eq=brightness=-0.18[bg];[0:v]scale=1080:-2[fg];[bg][fg]overlay=(W-w)/2:(H-h)/2

Wrapped into a runnable command:

ffmpeg -y -hide_banner -loglevel error -i input.mp4 \
  -filter_complex "[0:v]scale=1080:1920:force_original_aspect_ratio=increase,crop=1080:1920,boxblur=20:2,eq=brightness=-0.18[bg];[0:v]scale=1080:-2[fg];[bg][fg]overlay=(W-w)/2:(H-h)/2" \
  -c:v libx264 -preset veryfast -crf 21 -c:a aac -b:a 128k \
  -movflags +faststart short.mp4

Reading it left to right: scale=1080:1920:force_original_aspect_ratio=increase then crop=1080:1920 gives a background that fills the frame with no letterboxing; boxblur=20:2 and eq=brightness=-0.18 push it back visually so the foreground reads; scale=1080:-2 sizes the foreground to full width with an even height (mandatory for yuv420p); overlay=(W-w)/2:(H-h)/2 centres it.

One conversion takes roughly 20–60 seconds on a mid-range laptop CPU. That is the base unit of the whole pipeline: one long video in, one vertical Short out, at the cost of running a command.

Trimming to a moment

Add -ss (start) and -t (duration) before -i for a fast keyframe seek:

ffmpeg -y -ss 00:04:12 -t 42 -i input.mp4 -filter_complex "..." out_03.mp4

Step 2 — batch, and let audio pick the cuts

Doing clips one at a time works but does not scale. The useful version scans the source's audio energy and treats the peaks — laughter, emphasis, the moment someone lands a point — as clip boundaries. The audio tells you where the distinct moments are, so you are not guessing with a scrubber.

A minimal, dependency-free way to get an energy curve out of ffmpeg:

# dump mono 8 kHz PCM, then find the loudest windows in Python
ffmpeg -i input.mp4 -ac 1 -ar 8000 -f s16le -y audio.raw
import array, statistics
pcm = array.array("h"); pcm.frombytes(open("audio.raw","rb").read())
W = 8000                                    # 1-second windows
energy = [sum(abs(v) for v in pcm[i:i+W])/W for i in range(0, len(pcm)-W, W)]
thresh = statistics.mean(energy) * 1.35
peaks  = [i for i, e in enumerate(energy) if e > thresh]   # peak seconds

Group adjacent peak seconds, keep groups long enough to be a clip, expand each by a couple of seconds of lead-in, and you have a cut list you can feed straight into Step 1.

Why “distinct” is a compliance requirement, not a style choice

YouTube tightened its inauthentic content policy in July 2025 and enforced it in a January 2026 wave: mass-produced, templated or minimally-modified reused content is not eligible for monetisation. A Short that is your long video re-cropped five times is exactly that pattern. Five Shorts that are five different high-energy moments, each with its own hook, are not. Same source file, completely different risk profile — so build the batch step to enforce distinct moments rather than duplicating one.

Step 3 — a before/after proof reel

Three conclusions follow directly, and they contradict most advice on this topic:

  • Tags do not buy rank on a channel with no history. Ranking last on your own exact title is not a metadata problem, it is an authority problem. No amount of keyword stuffing fixes it.
  • Length is a 6× lever on the hardest monetisation gate. 320,000 views versus 53,000 for the same 4,000 hours. Chasing dozens of 60-second Shorts is the most expensive possible route to the watch-hour threshold — and Shorts pay far less per view than long-form in the first place.
  • Pick topics where the title-match is zero. The only queries worth building for are ones where the top results do not already answer the exact question. Score the competition before you write a script — pulling ten search results costs a fraction of the API budget of a single upload, and hours less than a render.

How to score a query yourself, cheaply, with the YouTube Data API: request search.list for the query, then channels.list for the result owners, and compute (a) median subscriber count of the top 10 and (b) the fraction of those titles that already contain your target phrasing. High subs + high title-match = do not bother. Low title-match against healthy view counts on adjacent videos = unserved intent.

FAQ

Does this need a GPU?

No. libx264 with -preset veryfast handles a one-minute vertical clip in well under a minute on a normal laptop CPU. GPU encoders (h264_nvenc) are faster but change quality-per-bitrate; CPU is the safer default.

Will the captions from my long video still be readable?

Yes — that is the reason the foreground is scaled to full width instead of being cropped. Burned-in captions keep their horizontal scale.

Is any of this against YouTube's rules?

Automating your own rendering and publishing is fine. What is penalised is mass-produced, minimally-modified, reused content. Make each clip a genuinely different moment with its own hook, disclose synthetic voice or AI assistance, and you are on the right side of the policy.

What does the free tier actually cover?

ffmpeg and Python are free outright. Pexels and Pixabay issue free API keys with generous rate limits. Fish Audio has a free TTS tier. The YouTube Data API gives 10,000 quota units per day — note an upload costs roughly 1,600 of them, so about six uploads a day is the real ceiling, and it is worth probing your remaining quota before an upload rather than eating a 403 that still burns the units.
